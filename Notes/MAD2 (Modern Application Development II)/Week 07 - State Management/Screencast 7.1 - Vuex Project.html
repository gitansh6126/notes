Why the Store Pattern

As a Vue app grows, data scattered across components becomes hard to track and easy to break. The store pattern fixes this by centralizing state into one place — a single source of truth every component can read from and request changes to.

01

The Four Pieces

Vuex plugs directly into Vue Devtools, which is what makes all of this inspectable.

data

State

The single source of truth — moved out of individual components so any of them can use it.

sync

Mutations

The only functions allowed to change state. Always synchronous. Triggered with commit().

read

Getters

A cleaner way to read state — and they can transform or format the data before returning it.

async

Actions

Handle complex or async logic, then commit a mutation once it's done. Triggered with dispatch().

What Belongs in the Store?

Not everything needs to be global — Vuex and local component data can coexist.

Keep Local

  • Data only one component uses
  • UI-only state, like a dropdown's open/closed flag
  • Anything that doesn't need to survive outside that component

Move to Vuex

  • Data multiple components need to read or react to
  • Application-level state — logged-in user, cart contents
  • Anything async operations need to update via actions
04

Key Takeaways

One store, one truth

Centralizing state keeps growing apps predictable instead of tangled.

Async → actions, only

Keep asynchronous work out of mutations entirely — dispatch an action, and let it commit once it's ready.

Debugging is a side effect

Because every change is an explicit, synchronous commit, Devtools can log — and reverse — the entire history for free.
