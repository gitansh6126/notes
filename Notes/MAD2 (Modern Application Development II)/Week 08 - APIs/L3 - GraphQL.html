Introduction to GraphQL

Last lecture's "chatty" REST problem — three round-trips for one screen — is exactly what GraphQL was built to close. One request, in the exact shape you asked for.

Analogy

Concept 1

The GraphQL Engine

A layer that sits between client and data — not a database itself.

The client sends a single POST request with a query body. The engine parses it, dispatches to whichever backend services or databases hold each field, fuses the results, and returns one shaped response.

✓
Data integration strength

Because the engine just orchestrates resolvers, one response can fuse a SQL user profile with a weather API's regional forecast — sources that would otherwise need to be stitched together client-side.

Concept 2

Type System

Every entity, field, and relationship is defined up front — this is what makes the API self-describing.

Schema definition

type Student {
  id: ID!
  name: String!
  courses: [Course!]!
}

type Course {
  title: String!
  grade: String
}

Self-documentation

The schema itself is the contract — what's available is never a guess.

Validation

Incoming queries are checked against the schema before any resolver runs.

⚖
No versioned endpoints needed

Because a query is a JSON-like object naming exactly the fields it wants, new fields can be added — or old ones deprecated — without breaking existing clients. Compare this to REST's usual /v1, /v2 endpoint versioning.

Concept 3

Resolvers

The functions that actually go get the data — one per field.

Resolver for Student.courses

courses(student) {
  // developer-written: told exactly how to fetch this field
  return db.query("SELECT * FROM courses WHERE student_id = ?", student.id);
}
A
Analogy

If the schema is the menu, resolvers are the individual kitchen stations — one for salads, one for grills. The engine reads the order and routes each part to the station that knows how to make it.

Concept 4

Mutations

Queries read. Mutations write — GraphQL's answer to create, update, and delete.

QUERY Read

Fetches data, shaped exactly as requested. No side effects.

MUTATION Write

Creates, updates, or deletes — and can still return the resulting shape in one round-trip.

✓
Full lifecycle in one language

Because both queries and mutations speak the same schema, GraphQL handles the entire data lifecycle — not just reads — without switching conventions.

Zooming out

GraphQL moves complexity — it doesn't remove it

The client got simpler. Something had to absorb that difference, and it's the server.

Where the cost lands

AreaWhat changes vs. REST
Server logicGrows — must parse, validate, and orchestrate multiple data sources per query
CachingHarder — a single POST endpoint defeats simple URL-based HTTP caching, so caching moves inside the server
Resolver designMust be deliberate — a careless resolver (e.g. one that triggers N further queries) can overload the server
!
Trap

"GraphQL reduces system complexity" — false. It relocates complexity from the client (multiple calls, manual stitching) to the server (parsing, validation, orchestration). Net simplicity depends on where that complexity is cheaper to manage.

⚖
When to reach for GraphQL

Favor it when clients have genuinely different data needs (web vs. mobile), when views are deeply nested/relational, or when you're fusing multiple backend sources into one view. Favor plain REST when endpoints are simple, caching at the HTTP layer matters most, or the team doesn't want resolver-level complexity to maintain.

Connections & traps

Where this fits, and where it's misread

Looking back: GraphQL is the direct answer to the chatty problem and over/under-fetching raised in Lecture 8.2's REST critique. Looking forward: resolver design, N+1 query problems, and schema stitching are the natural next layer once this foundation is solid. In industry: GitHub's v4 API and Shopify's Storefront API are both GraphQL, chosen specifically for their deeply nested, relational data.

✕
Exam trap

"GraphQL replaces the database" — false. It's a query layer/proxy in front of data sources; the database, third-party APIs, and other services are untouched underneath it.

✕
Exam trap

"GraphQL is always simpler than REST" — false. It's simpler for the client and more complex for the server; the total system complexity doesn't shrink, it shifts.

Active recall

Why doesn't GraphQL need versioned endpoints like /v1, /v2?
Because a query names exactly the fields it wants, new fields can be added or old ones deprecated on the same schema without breaking clients that never asked for them.
What's the actual job of a resolver?
A developer-written function, one per field, that tells the GraphQL engine how to fetch that specific piece of data from whatever source holds it.
Why is caching harder in GraphQL than REST?
REST's many distinct GET URLs are easy to cache at the HTTP layer. GraphQL funnels everything through one POST endpoint, so simple URL-based caching doesn't apply — caching has to move inside the server.
