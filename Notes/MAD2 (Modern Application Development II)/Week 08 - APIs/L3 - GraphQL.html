Introduction to GraphQL

A query language that trades REST's many fixed endpoints for one flexible endpoint — the client declares exactly what data it wants, and the server figures out how to assemble it.

Core Intuition (WHY)

🥪
Analogy — the buffet vs. the deli counter

A REST endpoint is a buffet tray: /students gives you the whole tray, whether you wanted three items or one. GraphQL is a deli counter — you tell the person behind the counter exactly which ingredients you want, in one order, and they assemble it from whichever stations (databases, other APIs) hold each ingredient. You place one order and walk away with exactly what you asked for, nothing more.

REST's pain

Need age + name + location filtered together? Either the endpoint supports that exact combination, or you download everything and filter client-side.

GraphQL's fix

The client's query names the fields it wants; the server's engine resolves each field from wherever it lives — one request, one shaped response.

Deep Fundamentals

Why was GraphQL created?
REST ties data shape to fixed endpoints. As apps needed to combine filters (age + name + location) or aggregate multiple services (user DB, weather, news) into one screen, REST forced either many round trips or bulky client-side filtering.
What problem does it solve?
Over-fetching (getting fields you don't need) and under-fetching (needing several requests to gather everything for one view) — by letting the client specify the exact shape of the response it wants.
What happens internally?
A GraphQL engine sits as a proxy layer on the server. It receives the query, validates it against a defined schema of types, then invokes a resolver function per requested field — resolvers may call a database, another REST API, or any data source.
How does this get executed?
The client sends the query as a JSON-like structure, typically via HTTP POST to a single /graphql endpoint. The engine parses it, checks it against the schema, resolves each field (possibly in parallel), and merges the results into one response.

Syntax Anatomy

query { student(id: 42) { name age school { name } } }
querydeclares this operation as a read — the GraphQL counterpart to GET
student(id: 42)a field with an argument — asks for one specific student, like a path parameter
name / agea selection set — only these fields come back, nothing extra
school { name }a nested field — follows a relationship in one request instead of a second round trip
💡 Tip
This structure is why queries are described as "JSON-shaped" — the query's shape mirrors the shape of the response you'll get back.

Real Project Usage

Facebook

Created GraphQL internally to power the News Feed, where one screen needs posts, comments, and profile data pulled together from many services.

GitHub API v4

Offers a full GraphQL API alongside its REST API, letting clients fetch a repo, its issues, and specific comment fields in a single request.

Shopify

Its Storefront API is GraphQL-based, so storefronts can request exactly the product fields they render, keeping mobile payloads small.

Netflix

Uses GraphQL-style federation to aggregate data from many internal microservices behind one query layer for its UI teams.

Common Mistakes

❌ WrongAssuming GraphQL removes complexity entirely
✅ CorrectIt shifts complexity from client to server-side resolver design
❌ WrongRelying on standard HTTP caching for GraphQL responses
✅ CorrectBuild server-side caching — requests are POST, so HTTP caching barely applies
❌ WrongWriting resolvers that each hit the DB per item in a list (N+1 calls)
✅ CorrectBatch and cache with a loader pattern to fetch related items together
❌ WrongVersioning the schema like REST (/v1/graphql, /v2/graphql)
✅ CorrectEvolve the schema by adding fields and deprecating old ones in place

Debugging Mindset

"A query with a list field is unexpectedly slow"
Problem: response takes seconds, not ms→ Observe: resolver logs show repeated identical DB calls→ Find stage: per-item resolver, no batching→ Fix: introduce a batching/caching loader
"One field in the response is null with an error"
Problem: field null, errors array populated→ Observe: resolver threw or data source returned nothing→ Find stage: that specific field's resolver→ Fix: check the resolver's data-fetch logic and args
"CDN caching isn't reducing load at all"
Problem: no cache hits at the edge→ Observe: every request is a POST→ Find stage: GraphQL requests bypass standard HTTP caching→ Fix: add an application-level cache inside the engine
⚠ Warning
A slow GraphQL API is almost always a resolver-design problem, not a query-language problem — trace it to the specific field before blaming GraphQL itself.

IITM Exam Pattern

Trigger Words

  • "ask for exactly what you need" → declarative query
  • "one endpoint for everything" → /graphql
  • "fetches one field's data" → resolver
  • "create/update/delete" → mutation

Trap Words

  • "GraphQL reduces overall complexity" — it shifts, not reduces
  • "GraphQL always uses GET" — it's POST-based
  • "no schema needed" — the type system is mandatory

MCQ Tricks

  • Option claiming GraphQL is "cacheable exactly like REST GET" → false
  • Option describing versioned URLs (/v2/graphql) → wrong, schemas evolve in place

PYQ Pattern & Elimination

  • Identify whether the scenario is a read (query) or a write (mutation) first
  • Eliminate any option that assumes GraphQL avoids server-side work entirely
  • Prefer options mentioning schema validation before resolution
🪤 Classic trap
A question may ask "does GraphQL reduce network traffic AND server load?" — it reduces network traffic (only requested fields returned) but can increase server load (one request now does the work of several). Don't mark both as unconditionally true.

Interview Questions

Easy
What is a resolver?
A function, written by the developer, that knows how to fetch the data for one specific field — from a database, another API, or anywhere else.
What's the GraphQL equivalent of POST for writes?
A mutation — the GraphQL construct for create, update, and delete operations.
Medium
How does GraphQL let an API evolve without version numbers?
New fields can be added to the schema and old ones marked deprecated, so existing queries keep working while new clients opt into new fields — no /v1, /v2 split needed.
Why is standard HTTP caching less effective for GraphQL?
Most GraphQL requests are POST with a query in the body, so URL-based HTTP caches (which key off GET URLs) can't distinguish or cache different queries the way they cache REST GETs.
Advanced
GraphQL is said to "shift complexity to the server" — explain concretely.
The client's query-writing gets simpler (one flexible request), but the server must now design resolvers carefully to avoid N+1 database calls, manage batching/caching, and validate arbitrary query shapes for cost — work that REST's fixed endpoints didn't require.
How would you defend against an expensive, deeply nested client query?
Techniques include query depth/complexity limiting, timeouts, and resolver-level caching — since the schema technically allows clients to request very expensive nested data in one call.
