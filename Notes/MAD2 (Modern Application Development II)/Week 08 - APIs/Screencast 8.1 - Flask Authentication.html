Module 2 · Core Intuition

Why does this exist?

A cookie is like a wristband stamped at a nightclub door — the club (browser) remembers it for you, and only works if you keep going back through that same door. A token is like a physical membership card you carry yourself — you can hand it to any counter (any client: mobile app, JS frontend, Postman) and they just check the card, no wristband, no club needed.

🎫 Analogy
APIs serve many kinds of clients — web apps, mobile apps, third-party scripts. A cookie only makes sense in a browser. A token works everywhere, because it's just a string you send in a header, like showing an ID card at any counter regardless of which building you're in.

Module 5 · Deep Fundamentals

The four core questions

1. Why was this feature created?

Because @login_required + session cookies assume a browser. Modern apps talk to APIs from JS fetch calls, mobile apps, and scripts — none of which want to babysit cookies or handle surprise redirects.

2. What problem does it solve?

It decouples "who are you" from "which browser session are you in." A token is portable proof of identity that any client can carry and present.

3. What happens internally?

Flask-Security-Too derives the token from the user's fs_uniquifier column using a signed serializer. The token is not stored raw in the DB — it is computed on demand from the uniquifier + a secret key, and validated the same way on every request.

4. How does the framework execute it?

On login with include_auth_token, Flask-Security-Too signs a payload derived from the user's id + fs_uniquifier. On each API call, auth_token_required reverses that signing to look up the user — no session, no cookie, no server-side session store needed.

Module 7 · Syntax Anatomy

Breaking down the pieces

User model — required column
class User(db.Model, UserMixin):
    # ...existing fields...
    fs_uniquifier = db.Column(db.String(255), unique=True, nullable=False)
  • fs_uniquifier a random, unique seed string per user — Flask-Security-Too uses it to derive that user's token
  • unique=True guarantees no two users can ever produce colliding tokens
  • nullable=False every user must have one, or token generation breaks
  • Reset trick: changing this value instantly invalidates the user's existing token — a built-in "log out everywhere" switch
Module 8 · Code Walkthrough

Step by step, with annotations

Step 1 — Configure the header name (optional)

config.py
SECURITY_TOKEN_AUTHENTICATION_HEADER = "Authentication-Token"  # default; can rename

Step 2 — Request a token

Client → POST /login?include_auth_token
fetch("/login?include_auth_token", {
  method: "POST",
  headers: { "Content-Type": "application/json" },
  body: JSON.stringify({
    email: "user@example.com",
    password: "secret123"
  })
})
  • ?include_auth_token tells Flask-Security-Too "also give me a token, not just a cookie"
  • JSON body must contain email and password — this is a normal login call, just with the extra flag

Step 3 — Protect an API endpoint with the token

resources.py
from flask_security import auth_required

@app.route("/api/items")
@auth_required("token")
def get_items():
    return jsonify(items=[...])
  • auth_required the modern generalized decorator — replaces the older cookie-only login_required
  • "token" tells it to validate via the header, not a session cookie
  • Missing/invalid token → returns 401 JSON error, never a redirect

Step 4 — Call the protected endpoint

Client → GET /api/items
fetch("/api/items", {
  headers: { "Authentication-Token": token }
})
Module 9 · Behind the Scenes

What the framework actually does

User row: id + fs_uniquifier
→
Signed with SECRET_KEY
→
authentication_token string
→
Sent back on future requests
→
Server re-derives + verifies signature

No token table, no server-side session store required for basic auth-token mode — the token is self-verifying: it's cryptographically signed data, not a random lookup key stored somewhere.

⚠️ Why changing fs_uniquifier resets the token
Since the token is derived from fs_uniquifier, changing that column changes what a "valid" signature looks like for that user — every old token instantly fails verification.

Module 11 · Common Mistakes

Wrong vs Right

❌ Wrong
Using @login_required on an API endpoint meant for AJAX/mobile clients → causes unwanted redirects to a login HTML page instead of clean JSON 401 errors.
✅ Correct
Use @auth_required("token") (or the older auth_token_required) for API endpoints so failures return proper 401 JSON responses.
❌ Wrong
Forgetting to add fs_uniquifier to the User model — token generation fails or throws errors at login.
✅ Correct
Add the fs_uniquifier column before enabling token features; migrate existing users to have a value.
❌ Wrong
Sending the token in the wrong header name (default is Authentication-Token, easy to confuse with Authorization).

Module 19 · Lecture Notes

Original Topic Content

This section contains the full original lecture content — the concepts, details, and explanations as taught in the screencast, outside the framework structure.

Overview

Modern applications often need to verify user identity across stateless API requests. Flask-Security-Too provides a token-based authentication system that works alongside (or instead of) traditional cookie-based sessions, enabling SPAs, mobile apps, and AJAX clients to authenticate reliably.

Cookie vs Token Authentication

Two Authentication Models

🍪 Cookie-Based Auth

  • Browser stores the session cookie automatically
  • Server maintains session state (or uses signed cookies)
  • Works seamlessly with server-rendered pages
  • On failure: redirects to login page
  • Depends on browser cookie mechanics

🔑 Token-Based Auth

  • Client stores token (e.g. Local Storage)
  • Server is fully stateless — token is self-verifying
  • Works with SPAs, AJAX, mobile apps
  • On failure: returns 401 JSON (no redirect)
  • Depends on cryptographic signing
Key Concepts

Flask-Security-Too Token Authentication

  • fs_uniquifier A required column on the User model. Changing it invalidates all existing tokens — useful for force-logout.
  • include_auth_token Query parameter on the login endpoint (e.g. /login?include_auth_token) to receive a token in the response.
  • Authentication-Token The default HTTP header name for sending tokens: Authentication-Token: <token>
  • @auth_required("token") Decorator that protects API endpoints. Replaces @login_required for token-based flows.
  • Token structure Cryptographically signed from: user ID + fs_uniquifier + SECRET_KEY. No server-side session store needed.
  • 401 Response Token failure returns a JSON 401 — never a redirect. This is critical for API clients that can't handle redirects.

When to Use Token Auth

Single Page Applications (SPAs) AJAX / Fetch API calls Mobile apps Postman / API testing Microservice-to-microservice auth
