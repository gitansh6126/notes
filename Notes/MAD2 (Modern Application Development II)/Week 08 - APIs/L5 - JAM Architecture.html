The JAMstack Approach

A methodology for building web applications by decoupling the interface from the data layer — trading server-rendered pages for pre-built markup, client-side JavaScript, and API calls.

01

The Problem: What Does Any App Actually Need?

Before comparing architectures, strip any web application down to its bare requirements. Every app — a blog, Instagram, your college portal — needs exactly three things.

Pillar 1

Data Storage

A persistent layer to hold application state — SQL, NoSQL, or GraphQL. Where the "truth" of the app lives.

Pillar 2

User Interface

The client-facing layer the user actually touches. Modern apps want this to feel instant and "native," not a slow round trip to a server.

Pillar 3

Business Logic

The computation on that data — split between the back end (Python, Node.js) and the front end (JavaScript, WebAssembly).

Analogy · The Restaurant

Think of a restaurant. Data Storage is the pantry and fridge — the raw ingredients. Business Logic is the kitchen turning ingredients into a dish. UI is the dining room where the customer actually experiences the meal. Every architecture choice in this lecture is really just a different answer to: "who owns the kitchen, and how far does the food have to travel to reach the table?"

02

CMS Evolution: One Roof → Separate Rooms

Traditional CMS platforms bolted all three pillars into a single monolithic system. Headless CMS pulls them apart.

Monolithic CMS — e.g. classic WordPress

Data storage, business logic, and the UI template engine all live inside one system. The server builds the full HTML page — including how it looks — every time it's requested. Change the front end, and you're touching the same codebase as the data layer.

Headless CMS — data with no fixed face

The back end manages content and exposes it purely through APIs. It has no opinion about how that content is displayed. Developers bolt on any front end they like — Vue, React, a mobile app — and the presentation layer is entirely delegated to the client side.

Analogy · The Ghost Kitchen

A monolithic CMS is a full-service restaurant: one kitchen, one dining room, one brand — all under a single roof. A headless CMS is a ghost kitchen: the kitchen (data + logic) still cooks the food and hands it out through a service window (the API), but it has no dining room of its own. Ten different delivery apps (React site, Vue site, mobile app) can all present that same food under completely different branding.

03

Static Site Generation — Cooking Ahead of Time

If a headless CMS separates the kitchen from the dining room, Static Site Generation (SSG) asks a different question: why cook the same dish to order for every single customer?

The Core Idea

An SSG pre-renders full HTML pages at build time, before any user ever asks for them. Instead of a server computing a page on every request, it serves an already-finished file straight from a CDN.

Analogy · Batch Cooking

SSG is a caterer who pre-cooks every dish the morning of the event, instead of firing up the stove per guest. When a guest arrives, the plate is already there — instant. If the menu changes, the caterer has to re-cook the whole batch (rebuild the site) — but each individual serving is now free and instant.

Hydration — Waking the Static Page Up

A pure static file can't respond to clicks. Hydration is the hybrid trick: ship the static HTML shell first (instant visibility), then let JavaScript "boot up" on top of it, attaching event listeners and turning a frozen page into an interactive one.

Build Time

Pages pre-rendered to static HTML

Happens once, ahead of any visit — not per user.

Request Time — Instant Paint

Browser receives finished HTML from CDN

The page is visible almost immediately — a fast "First Contentful Paint" (FCP).

Request Time — Hydration

JavaScript attaches interactivity on top of the shell

Buttons, forms, and dynamic behavior come alive without re-fetching the whole page.

Examples in the Wild

Next.js Nuxt.js Gatsby Jekyll Hugo
04

The JAMstack Philosophy

JAMstack isn't one specific tool — it's a methodology built by combining everything above. It names where each responsibility lives, not which framework to use.

J

JavaScript

Handles application logic and interactivity, running entirely on the client side after the page loads.

A

APIs

The interface for any dynamic data interaction — REST or GraphQL — reused across any number of front ends.

M

Markup

The presentation layer, pre-rendered ahead of time as static HTML or compiled from Markdown.

IITM Trigger — Reverse Recognition

If a question describes "pre-rendered markup + client-side JS + data fetched via API" in any order, it's pointing at JAMstack — even if it never uses the word.

06

Limitations & Where JAMstack Struggles

JAMstack optimizes for content that can be known ahead of time. It gets uncomfortable the moment "ahead of time" stops being possible.

Real-Time Communication

Apps needing low-latency, bi-directional flows — video/audio calls over WebRTC, live chat, collaborative editing — need more than static delivery and periodic API calls. The whole point of JAMstack (pre-build what you can) breaks down when nothing can be pre-built.

Immersive Interfaces — Future Outlook

Emerging interaction models — holographic displays, haptic feedback, VR/AR — may eventually demand an architectural shift the current web-page-and-API model can't easily absorb. JAMstack is a strong current answer, not a permanent one.
