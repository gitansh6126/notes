Module 2 · Core Intuition

Why does this exist?

Think of your Flask app as a house already fully built by Jinja — walls, rooms, doors all in place on the server. You don't want to demolish it to install one smart thermostat. Instead, you plug in a small smart device (Vue) into one room (a <div>) that reacts and updates on its own, while the rest of the house stays exactly as it was.

🏠 Analogy
A full Vue SPA would mean rebuilding the entire house as a smart home from scratch. The hybrid approach lets you keep the sturdy, SEO-friendly, server-rendered house — and only add reactivity exactly where you need it: a live search box, a dynamic sidebar, a counter.

Module 5 · Deep Fundamentals

The four core questions

1. Why was this feature created?

Not every app needs the complexity of a full SPA. Many teams have an existing Flask + Jinja app and just want one part of a page to feel modern and reactive — rebuilding everything as an SPA would be wasteful and risky.

2. What problem does it solve?

It lets you add client-side reactivity incrementally, without a build pipeline, without abandoning server-side rendering, and without losing SEO or breaking existing authentication.

3. What happens internally?

The browser receives one HTML page from Flask/Jinja. Somewhere in that HTML is a plain <div>. After the page loads, Vue's JS (loaded as a static file) scans for that div, "takes over" everything inside it, and starts managing it reactively — the rest of the page is untouched, static HTML.

4. How does the browser execute it?

Jinja renders and sends final HTML — before Vue ever runs. Only after the page loads in the browser does the Vue script execute, find its mount point, and begin reactive rendering purely on the client side from that point onward.

Module 7 · Syntax Anatomy

Breaking down the pieces

app.js — Vue instance anatomy
const app = new Vue({
  el: '#app',
  delimiters: ['${', '}'],
  data: {
    message: 'Hello from Vue!'
  }
})
  • el the CSS selector of the HTML element Vue should "take over" — this is the mount point
  • delimiters tells Vue to use ${ } instead of the default {{ }}, so Jinja never mistakes Vue syntax for its own
  • data the reactive state object — anything referenced here auto-updates the DOM when it changes
Module 8 · Code Walkthrough

Step by step, with annotations

Step 1 — Add Vue.js to your project

base.html — via CDN
<script src="https://cdn.jsdelivr.net/npm/vue@2"></script>

Step 2 — Mark the Vue mount point, avoid Jinja clashes

index.html (Jinja template)
<div id="app">
  <!-- Vue owns everything inside here -->
  {% raw %}
  <p>${ message }</p>
  {% endraw %}
</div>

<script src="{{ url_for('static', filename='app.js') }}"></script>
  • {% raw %} ... {% endraw %} tells Jinja "don't touch anything in here" — protects Vue's syntax from being misread as Jinja's own template variables
  • ${ message } Vue expression using custom delimiters — safe to sit inside a Jinja template because it no longer looks like {{ }}
  • url_for('static', ...) standard Flask way to reference the app.js file living in the static folder

Step 3 — Define the Vue app

static/app.js
new Vue({
  el: '#app',
  delimiters: ['${', '}'],
  data: {
    message: 'Hello from Vue!'
  }
})
✅ Two valid solutions to the curly-brace clash
Either wrap Vue expressions in {% raw %}, or change Vue's delimiters to ${ } — you don't need both, pick one consistently across the project.
Module 9 · Behind the Scenes

What each engine actually does

🍃 Jinja (server, runs first)

  • Runs entirely on the server, before any HTML reaches the browser
  • Replaces {{ }} expressions with real values at render time
  • Once the HTML is sent, Jinja's job is done — it never runs again for that page

🖼️ Vue (client, runs after)

  • Runs entirely in the browser, after the page has loaded
  • Scans the DOM for its mount point (el) and attaches itself there
  • Keeps watching its data and re-renders only that portion when it changes
⚠️ Why the clash happens
Jinja processes {{ }} during server rendering. If Vue also uses {{ }}, Jinja tries to render it first and either errors out or strips it — Vue never even gets a chance to see its own syntax.

Module 11 · Common Mistakes

Wrong vs Right

❌ Wrong
Writing {{ message }} inside a Jinja template expecting it to be a Vue expression — Jinja renders (or errors on) it first, so Vue never sees it.
✅ Correct
Wrap it in {% raw %}...{% endraw %}, or configure Vue's delimiters: ['${', '}'] so the two engines never compete for the same syntax.
❌ Wrong
Forgetting to load the Vue script before app.js runs — Vue won't be defined yet, causing a reference error.
✅ Correct
Load the Vue CDN/static script tag first in the template, then your own app.js after it.
❌ Wrong
Assuming this hybrid setup needs token-based auth like an SPA — it doesn't; standard Flask cookie sessions work fine since the page is still server-rendered.

Module 13 · IITM Exam Pattern

What to watch for in MCQs

Trigger: "same curly braces", "template conflict" Trap: assuming you need BOTH raw tags AND custom delimiters (only one is needed) Trap: confusing hybrid app with full SPA — hybrid keeps Jinja for most of the page
🎯 Elimination Technique
If a question implies rebuilding the entire frontend or removing Jinja entirely, eliminate it — the hybrid approach is defined by keeping Jinja for the bulk of the app.
📝 PYQ Pattern
Common question: "What causes template rendering conflicts between Jinja and Vue?" → Answer: both use {{ }} by default. "How do you resolve it?" → {% raw %} tags or custom Vue delimiters.
