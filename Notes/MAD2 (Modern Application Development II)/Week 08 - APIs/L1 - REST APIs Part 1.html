Designing APIs
Part 1

A good API reads like a sentence: a verb, acting on a noun, over HTTP.

Client requests
GET /students/123
⇄
Server responds — 200 OK
{ "id": 123, "name": "A. Kumar", "gpa": 8.7 }
no documentation needed to guess what this does — that's the point
01

What an API Is For

An API is a set of functions built for other developers to use — its whole job is to be an interface onto a system's logic and data. Designing with the developer in mind is what makes an API easy to document, test, and integrate.

Web APIs descend from Remote Procedure Calls, which let a client invoke a function on a remote server. They settled on HTTP as the transport because it's text-based, simple, and flexible enough to carry arbitrary request and response bodies.

02

Nouns and Verbs

Model the system's data as entities, and manipulate them with a small, standard set of actions.

Action (CRUD)HTTP VerbExample
Create a new entityPOST/students
Read an entityGET/students/123
Update an entityPATCH/students/123
Delete an entityDELETE/students/123

Even a query like "get this student's GPA" should be modeled as a logical endpoint — for example GET /students/123/gpa — rather than a one-off script.

03

URL Conventions

Conventions work like elevator buttons — familiar enough that no one needs the manual.

Avoid — verbs in the URL

GET /getStudents
POST /createStudent
POST /deleteStudent?id=123

Prefer — nouns + HTTP verbs

GET /students
POST /students
DELETE /students/123
04

Logical Path Hierarchies

A structured path reads naturally, top to bottom, left to right.

courses/ 123/ students
resource collection a specific ID → "the students enrolled in course 123"
05

Discoverability & Permalinks

Well-designed responses link onward, and the links they contain should never break.

Fragile identifier

/users/john_doe

Usernames can change. If they do, every bookmarked or shared link silently breaks.

Permalink

/users/123

A unique, unchanging ID keeps the link stable for as long as the resource exists.

06

Implementation Abstraction

The client only ever needs to know one language: HTTP.

Client
→
HTTP request
→
Flask
Node.js
Go

any of these could sit behind the API — the client can't tell, and shouldn't need to

07

Key Takeaways

Nouns in URLs, verbs in HTTP

Resources are addressed by path; actions are expressed through GET / POST / PATCH / DELETE.

IDs outlive names

Permalinks built on stable IDs won't break just because a display name changes later.

Design for the developer

Conventions exist so another developer can guess how your API works before reading a single doc page.
