Core Intuition (WHY)

🍽️
Analogy — the restaurant menu

An API is a restaurant menu with a very disciplined waiter. GET is "let me look at the menu again" — nothing in the kitchen changes. POST is "cook me something new." Before taking any order, the waiter checks your reservation card — that's authentication. Good API design isn't a rulebook enforced by police; it's shared etiquette that lets any client and any server understand each other on the first try.

Deep Fundamentals

Why were HTTP verb conventions created?
So that any client, proxy, browser, or cache — written by anyone, at any time — can predict what an endpoint does just from its verb, without reading custom documentation for every API.
What problem does this solve?
Without shared convention, every team invents its own semantics. Caches can't safely cache, retries become dangerous (what if a "read" secretly deletes something?), and tooling built for one API breaks on the next.
What happens internally when a request arrives?
The server's router looks at the verb + path together. A GET is routed toward a read path (often hitting a cache or read-replica); a POST is routed toward a write path that touches the primary database and returns the newly created resource.
How does this get executed in practice?
The framework matches method + URL pattern to a handler function, the handler authenticates the caller, performs the operation, and serializes the result — typically as JSON, often annotated with hypermedia links.

Real Project Usage

GitHub API

The textbook example of hypermedia — every response ships self and relationship links, so a client can "crawl" from a repo to its issues to a specific comment without hardcoding URLs.

Stripe

Uses POST for creating charges but adds idempotency keys, so retrying a payment request after a timeout can't accidentally double-charge — a pragmatic bend of pure REST theory.

Google APIs

Standardizes on OAuth 2 across every product (Gmail, Drive, Calendar) so one login flow and one token format work everywhere instead of each team rolling its own auth.

Twitter / X API

Uses JWT-based bearer tokens passed on every request, so the server can validate identity statelessly without a server-side session store.

Common Mistakes

❌ WrongUsing GET to delete or modify a resource
✅ CorrectUse DELETE / POST — GET must stay side-effect free
❌ WrongRolling your own authentication scheme
✅ CorrectUse OAuth 2 or JWT — battle-tested by the security community
❌ WrongReturning pre-rendered HTML from an API endpoint
✅ CorrectReturn structured JSON and let the front end render it
❌ WrongShipping responses with no self/relationship links
✅ CorrectInclude hypermedia links so the API is explorable and debuggable
❌ WrongTreating REST as a rigid law to obey at all costs
✅ CorrectBend it pragmatically when it improves developer experience

Debugging Mindset

"A GET-like endpoint is returning stale data"
Problem: same request, old result→ Observe: CDN/browser is caching→ Find stage: endpoint secretly mutates state on GET→ Fix: move mutation to POST, keep GET pure
"Every request returns 401 Unauthorized"
Problem: 401 runtime error→ Observe: console shows missing/expired token→ Find stage: auth middleware, before handler runs→ Fix: refresh JWT / re-attach Authorization header
"Client needs 6 requests to render one screen"
Problem: slow page, "chatty" warning→ Observe: waterfall of sequential GETs→ Find stage: no aggregation endpoint / no field filtering→ Fix: add an aggregate endpoint or a query-param filter
⚠ Warning
Breaking verb conventions is treated as a major design flaw in interviews and in exams — flag it every time you see it.

IITM Exam Pattern

Trigger Words

  • "safe to retry" → GET / idempotent verbs
  • "body carries the payload" → POST/PUT/PATCH
  • "crawl the API" → hypermedia / self links
  • "don't build it yourself" → OAuth2/JWT

Trap Words

  • "REST requires…" — REST is a style, not a spec
  • "JSON supports types like XML" — it does not, natively
  • "GET can modify if small change" — never true

MCQ Tricks

  • Option says "always follow REST strictly" → usually the wrong answer
  • Option mixes up cacheable (GET) vs non-cacheable (POST) → check verb first

PYQ Pattern & Elimination

  • Given a scenario, first identify the verb being described
  • Eliminate any option proposing custom-built auth
  • Prefer the option that favors developer usability over rigid theory
🪤 Classic trap
Questions may describe a "read-only" action but phrase it as modifying a counter (like a view count). Technically this is a side effect — many real APIs still use GET here pragmatically, but by strict convention it should be POST. Read the question's framing carefully.
14

Interview Questions

Easy
Why is GET cacheable but POST is not?
GET should never change server state, so identical requests can safely return a stored response; POST creates data, so caching it would return stale or incorrect results.
Why is JSON preferred over XML today?
JSON is more compact and easier for humans and parsers to read, even though it lacks XML's native type system.
Medium
What's the benefit of including self and relationship links in a response?
It lets a developer (or client program) discover and navigate the API dynamically instead of hardcoding every URL — the same way the GitHub API works.
Why avoid rolling your own authentication?
Custom auth code is far more likely to contain security bugs than OAuth 2/JWT, which have been extensively reviewed and hardened by the security community.
Advanced
REST doesn't natively support field filtering — how would you let a client request only a user's name instead of the full record, without breaking convention?
Common pragmatic solutions: query parameters (e.g. ?fields=name) or a GraphQL-style layer alongside REST — both bend strict theory in favor of usability.
When is it acceptable to break REST conventions?
Whenever rigid adherence would hurt the developer experience more than it helps — good API design is judged by usability, not textbook purity.
