Designing APIs — Part 2

A good API isn't the one that follows REST to the letter. It's the one a developer can guess correctly, without reading your docs. Four conventions make that possible — and knowing when to bend them is the real skill.

What kind of topic this is

Convention + trade-off judgment, not math. There's no formula to derive here — the "correctness" is social: does this API match what developers already expect from HTTP?

Concept 1

HTTP Verb Semantics

Map verbs (actions) onto nouns (resources) — and never surprise a developer who already knows what these verbs "should" do.

VerbIntentCacheablePayloadExample
GETRead-only retrieval, no DB modificationUsually yesURL / query paramsGET /users/7
POSTCreate new dataNoRequest bodyPOST /users
PUTReplace a resource fully, by conventionNoRequest bodyPUT /users/7
PATCHPartially update, by conventionNoRequest bodyPATCH /users/7
DELETERemove a resource, by conventionNoUsually noneDELETE /users/7

GET — the librarian

Fetches a book without rewriting it. Because it never changes state, the same question asked twice can safely reuse a cached answer.

POST — the intake clerk

Files a new form as a fresh record. Two identical submissions can create two different records — so caching it would be unsafe.

!
Trap: breaking verb conventions

A GET that silently deletes a row isn't a style nitpick — it breaks caching, prefetching, and every developer's mental model of "safe" requests. This is treated as a significant design failure, not a minor one.

R
Recognize it

A URL like /deleteUser?id=7 called via GET is the tell — the action leaked into the path instead of living in the verb.

Concept 2

Structured Data Output

Return data, not markup, so any client can render it its own way.

JSON — current standard

{
  "id": 42,
  "title": "Clean Code"
}
// terse, native to JS, easy to parse

XML — historically important

<book id="42">
  <title>Clean Code</title>
</book>
// verbose, richer typing/hierarchy
⚖
Judgment call

Need rich typing, namespaces, or schema validation across systems? XML still earns its keep. Building for a typical web/mobile client? JSON's lighter payload and native JS mapping make it the default.

Concept 4

Authentication Best Practices

Security is one place where "just build it yourself" is almost always the wrong call.

OAuth 2

Delegated access standard — a user grants a third-party app limited access without ever handing over their password.

JWT

A compact, signed JSON object carrying verified identity claims between client and API.

Works

Custom auth passes internal tests, ships on time.

Degrades

Edge cases — token replay, weak expiry — patched reactively.

Fails

An undiscovered flaw gets exploited. No community had a chance to catch it first.

!
Never true

"Home-rolled auth is fine just this once." Standards like OAuth 2 and JWT have been stress-tested industry-wide — a custom scheme hasn't, and that gap is where vulnerabilities hide.

Zooming out

"RESTful" is usually an approximation

Real REST APIs bend the original architecture constantly — knowing when that's the right call is the actual skill this lecture is teaching.

The "chatty" problem

Strict resource-per-endpoint design can force a client into many round-trips to assemble one screen.

Client
→
GET /book/42
Client
→
GET /authors/9
Client
→
GET /books/42/reviews

Three requests, one screen — this is the cost strict purity can impose.

Flexibility vs. purity

REST's core ideas — statelessness, cacheability, resource identification — are a foundation, not a cage. Letting a client pick which fields to return, for instance, is an acceptable deviation when it clearly improves developer experience.

Theory-firstDeveloper-first
⚖
When to bend the rules

Bend REST when a client needs a custom data shape every call (→ field selection), when one screen needs many resources (→ an aggregation endpoint), or when consumers are internal and iteration speed beats theoretical cleanliness. This is also exactly the gap GraphQL and gRPC were built to close.

Connections & traps

Where this fits, and where it's misread

A quick look outward before the recap.

Looking back: builds on Lecture 8.1's API fundamentals — resources, endpoints, basic REST. Looking forward: the chatty problem raised above is the direct motivation behind GraphQL (client-shaped queries) and gRPC (efficient binary RPC). In industry: GitHub's API is a hypermedia-discovery benchmark; Stripe's is praised for predictable verb usage.

✕
Exam trap

"REST is a strict standard with a fixed rulebook" — false. REST is an architectural style with guiding constraints; "RESTful" in practice is almost always a pragmatic approximation.

✕
Exam trap

"GET shouldn't be cached because data can change" — false. GET is cacheable precisely because it's expected not to modify state.

Active recall

Why is GET cacheable but POST isn't?
GET never modifies the database, so repeating it is safe and returns the same result. POST creates data, so identical requests can produce different outcomes — caching it would be unsafe.
Give an example of "bending" REST that's still good design.
Letting clients select which fields a response returns — a deviation from pure resource modeling that's widely accepted because it improves developer experience.
What problem does the self-link pattern solve?
It cuts reliance on external docs — a developer can discover related resources by following links inside the API's own responses, the way GitHub's API works.
