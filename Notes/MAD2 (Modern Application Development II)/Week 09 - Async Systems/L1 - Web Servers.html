Web Servers, Concurrency & Asynchronous Task Queues

How a server goes from "listening on a port" to "handing heavy work off to a kitchen full of background workers" — without ever making the client wait.

02

Core Intuition

Why
🛎️

A web server is like a hotel receptionist: it listens for guests (requests), checks them in, and sends a response. If the receptionist stops to personally cook a guest's dinner — a slow, heavy task — before checking in the next guest, the whole lobby backs up. Concurrency and task queues exist so the receptionist can say "order placed, we'll notify you" and immediately serve the next guest, while a separate kitchen staff (workers) prepares the food in the background.

05

Deep Fundamentals

No memorization

Why was this created?

Early web servers handled one connection at a time — simple to build, but the moment one request took long, every other user waited in line.

What problem does it solve?

Two problems: a bad user experience (blocked browsers, endless loading screens) and resource exhaustion (many heavy tasks at once can crash the server).

What happens internally?

A socket accepts the TCP connection, the request is parsed, and the server either handles it directly or hands it to a message broker that a separate worker is watching.

How does it get executed?

The OS scheduler juggles threads for concurrency; a broker like Redis or RabbitMQ queues the job; a worker process (e.g. Celery) pops it off and runs it independently.

07

Syntax Anatomy

Every keyword explained
  tasks.py
@app.task
def send_email(user_id):
    # ... heavy work happens here, off the main server ...
    email.send(user_id)
  • @app.task a decorator that registers this function as a background job Celery knows how to run
  • app the Celery application instance, wired up to a broker (e.g. Redis)
  • def send_email(user_id): an ordinary Python function — nothing special about the body itself
  • send_email.delay(user_id) (called elsewhere) — enqueues the job instead of running it inline; returns instantly
08

Code Walkthrough

Tiny example, line by line

❌ Blocking — inline in the view

  views.py
def upload(request):
    file = request.FILES['video']
    transcode(file)  # takes 3 minutes
    return Response("done")

The browser hangs for 3 minutes on this single request.

✅ Offloaded — queued as a task

  views.py
def upload(request):
    file = request.FILES['video']
    transcode.delay(file.id)
    return Response("processing")

The view returns in milliseconds; a worker transcodes in the background.

Call sequence

view()→ task.delay()→ broker.enqueue()→ worker.dequeue()→ task.run()→ result.store()

Behind the Scenes

What's really happening
Request arrives → OS assigns a socket
→
Threaded mode: a free thread from the pool picks it up
→
Heavy task detected: arguments get serialized
→
A message is published to the broker (e.g. a Redis list / RabbitMQ exchange)
→
Broker persists the message until a worker is free
→
An idle Celery worker polls, dequeues, and deserializes it
→
Worker executes the function and writes the result to a result backend

Common Mistakes

❌ / ✅
WrongRunning face-recognition or bulk email directly inside the request handler.
CorrectEnqueue it as a Celery task and return "processing" immediately.
WrongAssuming Python threading gives true parallelism for CPU-bound work.
CorrectUse worker processes (multiprocessing / separate Celery workers) for CPU-bound parallel work — the GIL limits threads.
WrongLetting the web server call the task function directly, with no broker between them.
CorrectPut a broker (Redis / RabbitMQ) in between so the server and workers stay decoupled and independently scalable.
12

Debugging Mindset

Problem → Fix

"Server hangs / times out under load"

Observe: timeouts under concurrent load → Find stage: check handler for blocking calls (sleep, sync I/O, heavy loops) → Fix: move the task to a queue; keep the handler light

"Task queue backlog keeps growing"

Observe: rising queue length in broker logs → Find stage: worker capacity vs. incoming request rate → Fix: scale the number of background workers horizontally

IITM Exam Pattern

MCQ survival kit
Trigger & Trap Words

Trigger words: "blocking", "thread", "concurrency vs parallelism", "task queue", "Celery", "message broker".

Trap words: options that describe a threaded server as running requests "in parallel" — that conflates concurrency with parallelism.

MCQ Tricks
Watch for statements claiming a single-core, threaded server achieves true parallel execution — a single core can only time-slice (concurrency), never truly parallelize.
PYQ Pattern
Expect definition-matching MCQs on concurrency vs. parallelism, and questions asking you to order the correct architecture: web server → message queue → worker.
Elimination Technique
If the question describes single-core time-slicing, eliminate any option using the word "parallelism" — and vice versa for multi-core execution.
14

Interview Questions

Three tiers
What's the difference between a threaded and a non-threaded server?
A non-threaded server handles one request at a time; a threaded server spawns a new thread per request so it can keep listening while one request is still being processed.
Why can't you just run a 2-minute video-processing job directly inside a Flask/Django view?
It would block that worker thread/process for the whole duration, degrading responsiveness for other users and risking resource exhaustion if several such jobs run at once — so it should be offloaded to a task queue instead.
Design the architecture for a system where users upload videos that need transcoding, with progress tracking.
Web server accepts the upload and returns a job ID immediately; the transcoding task is pushed to a broker; a pool of workers pulls jobs and updates progress in a result store (e.g. Redis); the client polls or subscribes for status using the job ID.
