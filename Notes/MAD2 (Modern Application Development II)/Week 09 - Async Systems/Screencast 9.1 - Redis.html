Core Intuition · WHY

The one idea behind everything

🗒️
A traditional database is a filing cabinet in the basement — organized, permanent, but a walk away every time you need something. Redis is the sticky note stuck to your monitor — nothing beats reaching for it, but you wouldn't trust it to hold your entire life's paperwork. Redis keeps everything in RAM, not on disk, so reads and writes are almost instant — at the cost of being less durable and less structured than a real database.

That single trade-off — speed over structure and permanence — explains every feature Redis has: caching, expiring keys, queues, pub/sub.

Deep Fundamentals

Why does this even exist?

1
Why created: Disk I/O is orders of magnitude slower than reading from RAM. Repeatedly hitting a disk-backed database for the same data wastes time.
2
Problem solved: Frequently-read, cheap-to-lose data (sessions, cached API responses, live scores) shouldn't have to pay the cost of a full relational database every time.
3
What happens internally: Everything lives in RAM as native data structures — hashes, lists, sets — addressed by a key. No tables, no SQL parser, no query planner.
4
How it executes: A single-threaded event loop processes commands one at a time, extremely fast, since there's no disk seek and no thread-locking overhead to fight through.
6
Execution Flow

What happens on a single command

a
Client sends SET session:42 "active" EX 3600 over TCP, port 6379
b
Redis's single-threaded loop receives and parses the command
c
The key-value hash table in RAM is updated with the new value
d
A TTL of 3600 seconds is attached to that key
e
Redis replies OK back to the client — all of this in well under a millisecond

Syntax Anatomy

Every piece, explained

SET user:101:name "Aditi" EX 120
SET the command — write a value under a key.
user:101:name the key — colon-separated namespacing is just a convention, not a required syntax.
"Aditi" the value being stored.
EX 120 optional flag — this key auto-deletes after 120 seconds (the TTL).

Call sequence: SET writes the key → optional EX attaches a countdown → TTL checks time remaining → key auto-vanishes at zero, no manual cleanup needed.
9
Behind the Scenes

What's actually happening under the hood

1
All keys live in one big in-memory hash table — lookups are near O(1)
2
A single thread handles commands sequentially — no locks needed, but also no parallel command execution
3
Expired keys are removed two ways: lazily (checked on next access) and actively (a background sweep samples keys periodically)
4
Optional persistence: Redis can snapshot to disk (RDB) or log every write (AOF) so a restart doesn't lose everything
Trade-off to remember: RAM is faster but finite and volatile. If your dataset grows past available memory, Redis starts swapping or evicting — plan capacity accordingly.

Common Mistakes

❌ Wrong / ✅ Correct

❌Letting your dataset grow larger than available system RAM
✅Keep the working dataset smaller than memory, or configure eviction policies for overflow
❌Treating Redis like a relational database with joins and complex queries
✅Use Redis for fast key-based lookups and caching; keep relational logic in an RDBMS
❌Storing ephemeral data (OTPs, sessions) with no TTL, letting memory bloat forever
✅Always attach an EX/TTL to data that's naturally temporary

Debugging Mindset

How to hunt down a memory problem

?
Problem: "Redis memory usage keeps climbing and won't come down."
1
Observe: Run redis-cli INFO memory and sample a few keys with TTL key.
2
Find stage: If TTL returns -1 on lots of keys, they were never given an expiry.
3
Fix: Add TTLs to the offending keys, or configure a maxmemory-policy like allkeys-lru to evict old data automatically.
